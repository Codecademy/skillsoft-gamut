## Installation and setup

1. Add gamut and peer dependencies

```bash
yarn add @skillsoft/gamut @emotion/react @emotion/styled
```

`@skillsoft/gamut` brings in `gamut-styles`, `gamut-icons`, `gamut-illustrations`, `gamut-patterns`, and `variance` automatically as regular dependencies, so no separate install is needed for those.

3. Wrap your application root with `GamutProvider` and give it the theme you would like to use for your app.

```tsx
import React from 'react';
import { render } from 'react-dom';
import { GamutProvider, theme } from '@skillsoft/gamut-styles';

import { App } from './App';

const rootElement = document.getElementById('root');

render(
  <GamutProvider>
    <App />
  </GamutProvider>,
  rootElement
);
```

GamutProvider handles a few critical tasks that need to happen in order for components to work.

1. Wraps components in the ThemeContext
2. Creates an emotion cache with our plugins
3. Adds Global styles and CSS Variables
4. Sets the current Color Mode context and variables.

**Note:** For react frameworks like Next and Gatsby this will be slightly different (see the SSR section for further steps for each framework). Your entry points for each framework will be:

- **Next** `_app.tsx`
- **Gatsby** `gatsby-ssr.js` `gatsby-browser.js` and use `wrapRootElement` in each.

5. Add required types for your theme, which will determine what props Gamut components allow.

```tsx
// theme.d.ts
import '@emotion/react';

// Import the appropriate theme shape `PlatformTheme` or `CoreTheme`
import { CoreTheme } from '@skillsoft/gamut-styles';

declare module '@emotion/react' {
  export interface Theme extends CoreTheme {}
}
```

For more information this declaration please checkout the [official emotion documentation](https://emotion.sh/docs/typescript#define-a-theme)!

6. Start Building!

```tsx
import { Background } from '@skillsoft/gamut-styles';
import { Text } from '@skillsoft/gamut';

export const App = () => (
  <Background bg="beige">
    <Text as="h1">Hello World!</Text>
  </Background>
);
```

### Content Security Policy (CSP)

If your app uses a strict Content-Security-Policy (e.g. `style-src` without `'unsafe-inline'`), pass a nonce to `GamutProvider` so Emotion and other Gamut-managed style tags are allowed:

```tsx
<GamutProvider nonce={yourCspNonce}>
  <App />
</GamutProvider>
```

Your nonce should be the same value you use in your CSP header (e.g. `style-src 'self' 'nonce-{value}'`).

## Module format: ESM vs. CommonJS

Every Gamut package ships **both** an ESM build (`dist/index.mjs`) and a CommonJS build
(`dist/index.js`), routed automatically by `package.json`'s `exports` map:

```jsonc
"exports": {
  ".": {
    "types": "./dist/index.d.ts",
    "import": "./dist/index.mjs", // `import { X } from '@skillsoft/gamut'`
    "require": "./dist/index.js" // `const { X } = require('@skillsoft/gamut')`
  }
}
```

**In almost every real app, you don't choose — your own code already does.** Whichever
syntax you import Gamut with is what selects the build:

```ts
import { FillButton } from '@skillsoft/gamut'; // -> dist/index.mjs (ESM)
const { FillButton } = require('@skillsoft/gamut'); // -> dist/index.js (CommonJS)
```

Every mainstream bundler (webpack, Vite, esbuild, Next.js, Rspack) and Node itself resolve
this correctly on their own. You only need to think about it explicitly in a few cases:

- **Running Gamut through native Node ESM with no bundler in front** (a plain
  `node --experimental-vm-modules` script, or similar). This is the one case where the
  `import` syntax genuinely matters: Node's native ESM resolver is stricter than a bundler's,
  and you must use `import` to land on the `.mjs` build.
- **A legacy CommonJS-only tool** that only understands `require()` — it gets the CJS build
  automatically via the `require` condition above; nothing to configure.
- **Mixing `require()` and `import()` of the same Gamut package in one process.** Node treats
  each condition as a genuinely separate module instantiation. For most components this is
  harmless, but anything relying on shared module-scope state (Emotion's cache, theme
  context) should stick to one import style per app rather than mixing both.

## Testing with Jest (and Babel)

Gamut depends on packages that ship modern JavaScript from `node_modules`. Jest often skips transpiling `node_modules`, so importing Gamut in tests can surface parse or syntax errors unless your repo opts those dependencies into your test transform.

If tests only fail after upgrading Gamut or a transitive dependency, compare your Jest and Babel setup with Gamut's and adjust `transformIgnorePatterns` and plugins accordingly.

Jest's default module resolution is CommonJS-based, so a plain `require('@skillsoft/gamut')` inside a test resolves through the `require` condition above and gets the already-built CJS `dist/index.js` — no transform needed for Gamut itself. This only changes if your Jest config is set up for native ESM (`extensionsToTreatAsEsm`, `--experimental-vm-modules`); in that mode Jest resolves the `import` condition instead and gets `dist/index.mjs`.

### `transformIgnorePatterns`

Allow your test transformer (for example `babel-jest`) to run on specific packages. Gamut's own Jest setup uses a negative lookahead so `@vidstack/react` and `@formatjs` are not ignored:

```js
// jest.config.js (or equivalent)
transformIgnorePatterns: ['node_modules/(?!(@vidstack/react|@formatjs)/)'],
```

Add more package scopes inside the non-capturing group if your tree pulls in other untranspiled ESM (for example `|@your-scope`).

### Babel and newer syntax

Even when those packages are transformed, older Babel configs may not handle every language feature.

To fix that, the necessary plugins need to be added to the Babel config Jest uses, or upgrade **`@babel/preset-env`** / Babel so that feature is covered.
